# crowdfund

A crowdfunding escrow contract (funding target + deadline), generated by
[soroban-forge](https://github.com/soroban-forge-labs/soroban-forge) from the
`crowdfund` template.

## How it works

1. The contract is deployed with an `owner`, a pledge `token`, a `target`
   amount and a `deadline` (unix timestamp).
2. Backers call `pledge(from, amount)` before the deadline; tokens are held in
   escrow by the contract.
3. After the deadline:
   - target reached → `claim()` sends all funds to the owner (once);
   - target missed → `refund(to)` returns each backer's pledge.

## Storage lifetime

The constructor and successful `pledge`, `claim` and `refund` calls renew the
campaign instance. Pledge writes and existing-pledge reads (including
`get_pledge`) renew that backer's persistent entry. Named ledger constants
renew a lifetime at or below 29 days to 30 days, assuming five-second ledger
closes. Reading an unpledged address returns zero without creating an entry.

TTL is measured in ledger closes; the campaign deadline remains a unix
timestamp. Renewal preserves the existing amounts, claim/refund rules and
authorization. Inactive instances or pledge entries can still archive after
their extended lifetime and require restoration. Renewal does not restore
already archived state, and reading one pledge does not renew other backers.

The tests check recorded lifetimes before advancing beyond the network's
default persistent TTL, then exercise claim and refund with local token
fixtures. This avoids mistaking the SDK's test-only auto-restoration for
production TTL retention.

## Develop

```sh
cargo test
stellar contract build
```

## Deploy to testnet

```sh
stellar contract deploy \
  --wasm target/wasm32v1-none/release/crowdfund.wasm \
  --source-account <your-identity> \
  --network testnet \
  -- --owner <OWNER_ADDRESS> --token <TOKEN_ADDRESS> --target 10000000 --deadline 1790000000
```
